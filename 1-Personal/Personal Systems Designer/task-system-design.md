# task-system-design

[Personal Systems Designer](README.md) / [Personal domain](../../README.md)

## Purpose

Define capture, clarification, selection, tracking and closure for actionable commitments.

## Activate When

Commitments and next actions are being missed, duplicated or checked across too many places.

## Do Not Use When

Knowledge, calendar events and someday ideas are not all tasks.

## Required Context

**Needed**

Current capture points, calendars/lists, commitments, task volume, review habit, collaboration constraints, recurring failures and tool limits.

**Can be deferred or bounded**

Optional metadata and automation wait until the minimal loop works.

## Workflow

1. Inventory trusted and untrusted sources, then sample misses and duplicate work. Separate appointments, actionable commitments, projects and reference.
2. Choose one default inbox, one authoritative calendar and one trusted task source where feasible. Define a minimal task with action, owner/context and relevant due constraint.
3. Design capture, clarify, do/defer/delegate, project next-action, waiting and review flows. Migrate only active commitments first and preserve rollback.
4. Run the system through busy and disrupted weeks; measure missed commitments, places checked, stale tasks and review time before adding fields or AI.

## Trusted Commitment Loop

A task system should reduce remembering and checking, not model the entire person. Due dates represent real constraints, not anxiety. Calendar holds time-specific reality; reference material is not a task.

## Decision Rules

- Start with the minimum fields needed to act and review.
- When multiple tools cannot be removed, define authority and synchronization explicitly.

## Output Contract

Task-system specification with object boundaries, sources of truth, capture/clarify/execute/review flow, migration, disruption fallback and success measures.

## Quality Gates

- Every active commitment has one authoritative representation.
- The weekly review can be completed within sustainable time.

## Failure Modes

- **Building a complex database before trust exists:** pilot minimal loop.
- **Migrating the entire backlog imports stale guilt:** re-decide active commitments.

## Handoffs

Planner owns which work fits; PKM stores supporting knowledge; Automation may reduce stable mechanical steps later.
