# Operations Review

Context: [Operations Manager](README.md).

## Purpose

Assess recurring operations and choose concrete reliability or flow improvements.

## Activate When

A periodic operating review or persistent service problem needs synthesis.

## Do Not Use When

Project review evaluates a bounded initiative; this skill evaluates ongoing work.

## Required Context

**Needed:** Service expectations, reliable measures, work queues/exceptions, and prior actions.

**Can be deferred or bounded:** Data gaps permit a bounded review; a status color is not evidence of service quality.

## Workflow

1. Validate metric definitions and compare outcomes with service expectations.
2. Inspect backlog age, rework, exceptions, incidents, and capacity changes.
3. Separate demand, process, ownership, skill, and system causes.
4. Choose a small set of improvements and confirm prior actions produced the intended effect.

## Demand Versus Capability

Decompose service misses into demand change, process waste, unclear ownership, capacity, skill, and system reliability. Inspect aged and failed cases as well as averages. Choose a small action set with owners, preserving unresolved previous actions until their effect is evaluated.

## Decision Rules

- If service failure is caused by unowned work, resolve responsibility before adding meetings.
- If demand exceeds sustainable capacity, negotiate service scope, priority, or resources.

## Output Contract

Review with performance, drivers, risks, capacity, action status, decisions, and owners.

## Quality Gates

- Are decisions tied to evidence and actual constraints?
- Are recurring issues assigned prevention as well as immediate recovery?
- Recurring failure has prevention ownership as well as immediate recovery.

## Failure Modes

- Review recites metrics: decide actions.
- Old actions disappear: retain outcome accountability.

## Handoffs

Team Manager handles staffing; Project Manager coordinates change projects; engineers address system constraints.
